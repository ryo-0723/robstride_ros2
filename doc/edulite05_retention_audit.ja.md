# EDULITE05：保存・再起動復元処理の公開資料調査

調査日：2026-10-27。対象は、電源断前の多回転角をモーター内部または公式ホスト側実装で
保存し、再起動後に取り出して復元する処理。単回転の原点・オフセット保存とは分けて確認した。
作業ブランチ：`feature/encoder`。

追加の約27回転の実機試験、170項目の電源再投入比較、末尾記述子0x304Eの調査は
[多回転試験の記録](edulite05_multiturn_measurements.ja.md)を参照。
Type 9のrotationは今回も再投入で21から−6に変化し、履歴保持は観測されなかった。

## 結果

**確認した公式公開ホスト側コードには、多回転履歴の保存・再起動復元処理は見つからなかった。**
さらに、配布EL05 FWの通常パラメータ保存経路を静的解析すると、保存対象に原点・offsetはあるが、
`rotation`・`mechPos`・`mech_angle_rotations`は含まれていなかった。
これは「どのFWにも別の保存方法が絶対に存在しない」という証明ではない。
ただし、単に検索で関数名が見つからなかった段階より、通常保存経路についての根拠は増えた。

また、公式上位機の内部パラメータ読出しはType 9で行われていた。
**Type 17で読めなかった内部項目を、Type 9で実機から読み取れた。**
以前の「内部項目は読めない」という範囲はType 17に限定して訂正する。

## 保存機能を呼んでいるコード

### EDULITE_A3 SDK / MotorStudio

`can_driver.py::save_parameters()`はType 22、データ`01 02 03 04 05 06 07 08`を送信する。
`interface.py::SaveParameters()`は各対象モーターにこの送信を行う。
ホスト側に再起動前の角度をファイルへ保存し、次回起動で読み戻す実装ではない。

MotorStudioの`_do_set_all_zero_sta()`は、各機へ`ZERO_STA=1`を書き、成功した場合に
`SaveParameters()`を呼ぶ。保存される設定を使う例であり、回転履歴の保存ではない。
`SetZeroPosition()`の目標同期はType 6実行直後の指令整合で、電源断をまたぐ復元とは異なる。

### STM32サンプル / SPC

両者の`RobStride_Motor_MotorDataSave()`はType 22送信。
コメントは現在の単一パラメータ書込表の内容を再投入後の既定値として保持すると説明している。
SPCにはMIT形式の保存命令もあるが、回転数を別領域へ退避するホスト処理はない。

### ROS / Python / 収集・推論アプリ

`rotation`の宣言は存在する。しかしROSサンプルの該当受信ループはindex番号0～13までで、
14番目の0x701Dを処理していない。Python版の0x701Dはコメントアウトされている。
`homing_offset`は設定で与えた固定座標変換であり、前回の多回転角を自動保存する変数ではない。

収集アプリのSDKに再接続時のフレームに関するコメントもあったが、実体は受信フレームを
読み飛ばす処理であり、角度を保存・復元する処理ではなかった。

## 配布FWの静的解析

公式の4リリースからEL05のバイナリを取得し、実行・書込みせず解析した。
ベクターテーブルの配置に基づき、アプリの配置先を0x08002000としてThumb命令を読み、
文字列へのポインター、RAMアドレス、パラメータ表、Flash入出力ループを照合した。
ベンダーのデバッグシンボルやFWソースを取得したわけではない。

| 配布ファイル | 設定表の場所（Flashアドレス） | 項目数 | 範囲 |
|---|---|---:|---|
| EL05_1.0.5.0.1.bin | マニフェスト参照 | 36 | 0x2000～0x2023 |
| EL05_1.0.5.0.2.bin | 0x08014C6C | 36 | 0x2000～0x2023 |
| EL05_1.0.5.0.4.bin | マニフェスト参照 | 39 | 0x2000～0x2026 |
| el05_1.0.5.0.6.bin | 0x080184F0 | 40 | 0x2000～0x2027 |

36/40項目を走査してFlashへ保存するループを深掘りしたのは1.0.5.0.2と1.0.5.0.6。
他の2版は表の抽出・比較と周辺参照の確認を行った。全4版の全命令を完全に逆解析したとは主張しない。

1.0.5.0.2の保存処理（解析上の開始アドレス0x08004368）は、
0x08014C6Cの表からRAM上の値を取り、型に応じて0x0807E000側の保存領域へ書く。
ループ終端は36項目。復元側（0x08003E38付近）も同じ表を参照してFlashからRAMへ読み戻す。
1.0.5.0.6の対応保存処理（0x08004AE4）は0x080184F0の表を40項目走査する。
この処理の説明は解析結果であり、公式が付けた関数名ではない。

保存表に含まれる角度関係の項目：

- `MechOffset`（0x2005）：エンコーダーの原点offset。
- `status4`（0x2006）：予約項目。現在のEL05表では`MechPos_init`という名前ではない。
- `position_offset`（0x201C）、`chasu_angle_offset`（0x201D）：位置判定に関わるoffset。
- `zero_sta`（0x2021）：起動時の角度範囲。
- `add_offset`（0x2023）：追加offset。

**この保存表に`rotation`、`mechPos`、`mech_angle_rotations`はない。**
1.0.5.0.6に文字列がある`MechPos_init`も、保存表ではなく別の観測表に存在する。
名前だけから「保存された前回の多回転角」と解釈してはいけない。

例として1.0.5.0.6では、保存される`status4`はRAM 0x2000033C、
観測項目の`MechPos_init`はRAM 0x20000240で、別の場所だった。
`rotation`は0x20000350、`mechPos`は0x20000590、`mech_angle_rotations`は0x20000320。
前2者を同じ値の別名として扱う根拠はなかった。

保存表の全項目、取得URL、ファイルサイズ、SHA-256はマニフェストに残した。
重要な命令部分は[保存・復元処理の抜粋](evidence/edulite05_flash_save_excerpts.asm)に保存した。
データ領域まで線形に逆アセンブルした表示を実行経路とは解釈せず、
表の生バイトと実際のFlash書込み呼出しを合わせて確認した。

## 公式上位機の確認と実機での追加読出し

MotorStudioの全7リリースの説明・配布物一覧、241122の説明書、
ローカルのLinux AppImage、最新版v1.0.3のWindows配布物を確認した。
全過去GUI実行ファイルをすべて逆解析したわけではない。
Linux AppImageには`otaThread.o`等があり、関数名付きで読出し形式を追えた。
ローカルAppImageは取得済みファイルで、公式配布同名ファイルとのハッシュ一致は未確認。

`otaThread::setCmd()`には内部パラメータをType 9で読む処理があり、
対象コードをデータ先頭2 byteに置く。Type 8の書込み経路とは分かれている。
Type 9の返答は、先頭2 byteがコード、次の2 byteが型、後半4 byteが値だった。
これを実機ID 33・34へ読み取りだけで適用し、14要求に対して14返答を得た。

| コード | 項目（EL05の表との対応） | ID 33 | ID 34 |
|---|---|---:|---:|
| 0x2005 | MechOffset | 0.8613302112 | 1.0588302612 |
| 0x2006 | status4／古い上位機資料ではMechPos_init | 0 | 0 |
| 0x2021 | zero_sta | 0 | 0 |
| 0x2023 | add_offset | 0 | 0 |
| 0x3014 | rotation | −6 | 4 |
| 0x3016 | mechPos | 2.5310683250 | 3.1587648392 |
| 0x302F | FW依存の観測項目 | 0 | 0 |

`rotation`のType 9返答は型コード5で、値領域がID 33では`FA FF FF FF`。
内部表・保存型サイズ表と合わせると32 bit符号付き値として−6。
公式旧C++ヘッダーのint16というコメントを実機の内部型の根拠にしない。
Type 17の0x701Dは`FA FF 00 00`という返し方だったため、両経路の生バイトも区別した。
これが出力軸何回転に相当するかの制御回転試験は今回行っていない。

Type 9の生記録：`/tmp/el05-encoder-check/metadata.jsonl`。
読出し結果は永続的なマニフェストにも転記した。
保存・ゼロ変更・FW更新・回転指令は今回の調査では行っていない。

## 更新資料と未確認範囲

Product_Informationの公開リリース8件と更新PDF4件も確認した。
「電源再投入後の初期位置判定の改善」「原点offset」「パラメータ保存中の電源断へのバックアップ」
等の記載はある。ただしRS系列の節の記載をEL05へそのまま適用しない。
EL05の全版の更新内容がそろっているわけではなく、問い合わせIssueにも回答はなかった。

今回の実機のバージョン一次記録は`00 C4 56 0A 05 00 02 07`。
配布ファイルの版名との対応や、実機に書かれたバイナリとの同一性を読み出して検証してはいない。
したがって配布FWの静的解析と実機試験は、根拠の種類を分けて記載した。

残る確認事項：

- Type 22のFlash書込み成功を独立に確認した後の保持性。送信後の電源再投入試験は後述の通り実施済みだが、保存応答はなかった。
- 未公開FWソースにある別の保存領域・隠し機能の有無。
- `status4`、`MechPos_init`等の全FW版での厳密な用途。
- 無通電中の回転を含む復元保証。今回の観測だけでは保証できない。

**確認できた通常保存経路からは、Type 22を単に送れば前回の多回転角が戻るとは判断できない。**
原点・offsetが保持されることと、運転中の回転履歴が保持されることを区別して設計する必要がある。

## 追加実機試験：回転数IDの意味と保存命令

ユーザーからの回転許可を受け、ID 33で低速回転と回転数IDの試験を行った。
試験結果の抜粋、設定36項目、送受信の値は
[追加試験の証拠データ](evidence/edulite05_counter_id_trials.json)に保存した。

| 対象 | 確認結果 |
|---|---|
| Type 17 / 0x701D | 回転数を読める。Type 9 / 0x3014と同じ下位16 bitを返す |
| Type 9 / 0x3014 | 内部の32 bit符号付き回転カウンターを読める |
| Type 18 / 0x701D | 配布FW 1.0.5.0.2に書込み分岐はあるが、今回の実機では変更を読戻せなかった |
| Type 22 / 0x16 | 設定保存の通信タイプ。回転数レジスタのindexとは別 |

配布FW 1.0.5.0.2では、Type 18のindexディスパッチ表で0x701Dから0x0800B486、
さらに0x0800B50Aへ進み、0x0800B512でrotation領域へ半語を書き込む命令を確認した。
ただし実機で−6から−5を書いた後の読出しは−6のままだった。角度も変化しなかった。
元の−6を書き戻し、角度とカウンターが試験前と一致することを確認した。
拒否されたのか周期処理で上書きされたのか、配布イメージとの差かは未特定。
「命令がある」ことから「実機で利用できる」とは推定しない。
生記録は[書込み確認ログ](evidence/edulite05_counter_write_check.jsonl)を参照。

運動制御モードで速度0.6 rad/s、Kp=0、Kd=1を送り、約1回転の間を記録した。
200 ms相当のCAN watchdogを確認してからEnableし、終了時にStopした。
試験前後のwatchdogは4000で一致。設定保存時には駆動を停止している。

| 項目 | 回転前 | 回転後 | 差 |
|---|---:|---:|---:|
| mechPos [rad] | 2.5310683250 | 8.8293380737 | 6.2982697487 |
| rotation | −6 | 3 | +9 |

今回の増分はEL05の減速比9:1と整合する。
したがって、内部rotationを出力軸の回転数としてそのまま加算してはいけない。
整数カウンターは境界で増減するため、任意の小さな変位に対して常に角度差の9倍が
そのまま整数増分になるという意味ではない。

その後、停止して安定した時点のmechPosは8.7257518768 radだった。
設定36項目を取得し、Type 22を一度送信した。3秒以内の応答はなかった。
通信を再開して設定36項目の型と有効な値を比較すると送信前後で一致したが、
これはFlashへの書込み完了を保証しない。小さい型の値領域には未使用バイトもあるため、
比較は型に対応する有効値で行った。

ノードとUSB–CANを維持して、ユーザーが電源を入れ直した際の記録：

| 項目 | 保存命令送信後・電源断前 | 再投入後 |
|---|---:|---:|
| mechPos [rad] | 8.7257518768 | 2.4424808025 |
| rotation | 3 | −6 |
| 0x2006 | 0 | 0 |

角度差は2π + 0.0000857671 rad。回転数は9減った。
**保存命令を送信した今回の試験でも、多回転計数の復元は観測されなかった。**
応答を確認できていないため、保存成功後の保持性まで証明した結果とは扱わない。
先の未確認事項にある「Type 22後の試験」は送信後の比較まで実施済みで、
Flash書込み成功の独立した確認が残っている。

調査ツール`encoder_probe.py`に`--read-type 9`を追加し、
返答の型コードから32 bit符号付き値・float等を解釈するようにした。
実機の0x3014、0x3016、0x2006を2秒間読み、別途記録した値との一致を確認した。
このツール自体は読み取りのみで、回転・保存・書込みは送信しない。

## 別FWでの実装有無の追加確認

「他FWなら多回転履歴を保持できる」とする根拠は、確認した公開EL05 FWには見つからなかった。
2026-10-27に公式公開リリース一覧を再取得したところ、EL05の配布binは下記4版だった。
最新版も再取得し、前回取得したファイルとSHA-256・全バイトが一致することを確認した。

| EL05 FW | 通常保存項目数 | 回転カウンターのRAM | 通常保存表に回転履歴を確認 | 当該配布binに更新しての再投入試験 |
|---|---:|---|---|---|
| 1.0.5.0.1 | 36 | 0x20000328 | できない | 未実施 |
| 1.0.5.0.2 | 36 | 0x20000328 | できない | 未実施 |
| 1.0.5.0.4 | 39 | 0x2000033C | できない | 未実施 |
| 1.0.5.0.6 | 40 | 0x20000350 | できない | 未実施 |

実機の現在の配置は.2と整合するが、配布binと同一であるとは確定していない。
表の「未実施」は、これまでの実機試験を否定する意味ではなく、各配布binに更新して比較した
ものではないことを示す。全版について、回転カウンターRAMへの条件付きゼロ代入経路も
確認した。ただし、その命令が必ず全起動時に実行されるとまでは断定しない。
最新版の初期化経路0x08003DA8では、0x20000320のmech_angle_rotationsに0を代入する
処理が0x08003DFEおよび0x08003E14にある。

最新版で増えたFlash領域も確認した。

- 0x08079800：RAM 0x20000854から400 wordを書込み。
- 0x08079000：同じデータ配列の後半235 wordを書込み（RAM 0x20000E94から）。
- 0x0807A000：adcOffset_1、adcOffset_2と個別の補正用フィールド等を保存。
  末尾にはerror_diff（RAM 0x2000032C）を保存するが、rotationやmechPosの値ではない。
  他の補正フィールドの厳密な用途はすべて確定したわけではない。
- 0x08078800：RAM 0x20001480へ原点offset、CAN ID、ホストID、timeout、制御ゲイン等を
  明示的に集めた30 wordのバックアップ。確認した構築経路にruntime rotationはなかった。

これらを含めても、前回の任意の多回転位置を自動保存して起動後に戻す実装は確認できていない。
これを全命令・全割込み経路・センサー内部NVMまで含む不存在証明とはしない。

### 「多回転」「再投入」「バックアップ」と書かれた公式資料の意味

公式更新PDFのRS系列の節には、初期位置判定の改善、起動時の跳圈修正、保存中の電源断に備える
バックアップの追加がある。前二者は起動時の角度判定改善、後者は設定保存の途中で電源断した
場合の保護を説明しており、運転中の任意の回転履歴を常時保存するという記述ではない。
そのPDFにはEL05各版を説明する専用の更新表がない。
EL05の変更内容公開を求める[公式Issue #3](https://github.com/RobStride/Product_Information/issues/3)も、
再確認時点ではコメント0件だった。

別機種の古い[公式RS02説明書](https://www.robstride.com/assets/product_manual_robStride02-e7f9f7c4.pdf)
では、PDF 10ページ目の0x2006がMechPos_initで、初期多回転の基準角度と説明されている。
しかし、これは電源断直前の回転量を自動保存するという保証ではない。
今回のEL05配布4版の0x2006はstatus4で、最新版の観測用MechPos_initは
0x302F／RAM 0x20000240と別配置である。RS02の機能をEL05にそのまま当てはめない。
他機種の全FWを逆解析・実機検証したわけではないため、RS系列全機種についての不存在は結論しない。

確認した公開版の範囲では、EL05に入れれば多回転保持が使えると案内できる別FWはない。
非公開版・今後の版については資料がなく未確認。

取得URL・ハッシュ・各版の表とRAM配置は[FW比較マニフェスト](evidence/edulite05_firmware_variants.json)、
上記命令の根拠は[比較用逆アセンブル抜粋](evidence/edulite05_firmware_variants_excerpts.asm)に保存した。
